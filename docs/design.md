## 阶段1：命令行聊天

### 1. 整体结构

系统由客户端、服务端和共用通信模块组成。客户端将命令编码为请求；服务端接收完整消息，按请求类型调用业务处理函数，再通过连接对象返回响应。协议层负责消息格式，网络层负责字节收发。

以`message`作为消息基本单位，包含请求类型以及JSON格式正文。

```text
客户端命令 → Message → 协议编码 → TCP
                                  ↓
客户端显示 ← 协议响应 ← 请求处理 ← 协议解码
```

#### 1.1 工程与模块组织

| 文件 | 职责 |
| --- | --- |
| `common/net.h`、`common/net.cpp` | 循环收发指定数量的字节，处理部分读写及信号中断 |
| `common/protocol.h`、`common/protocol.cpp` | 定义消息对象，编码和解析协议帧 |
| `common/error_codes.h` | 集中定义错误码字符串，保持响应标识一致 |
| `server/main.cpp` | 创建监听 socket、接受连接、启动工作线程 |
| `server/session.h`、`server/session.cpp` | 登录、在线列表、请求分发及连接结束后的用户清理 |
| `server/connection.h` | 管理通信描述符的生命周期和整帧发送锁 |
| `client/main.cpp` | 解析终端命令、发送请求、独立接收并显示消息 |

#### 1.2 网络与并发模型

服务端采用一连接一线程。主线程循环调用`accept`，将返回的通信描述符交给分离的工作线程执行`handle_client`，随后继续接受新连接。每个工作线程顺序接收、处理和响应本连接的请求。监听socket由主线程管理，通信socket由对应的**连接对象**管理。

客户端主线程负责键盘输入和发送，另一个接收线程持续调用 `recv_message` 并显示 JSON。只有接收线程读取 socket，避免多个读取者分走同一帧的数据。接收过程不依赖用户是否正在输入。

#### 1.3 连接对象与在线用户表

管理通信socket的结构体`Connection`，包含该socket的文件描述符以及对应的线程锁，使用共享智能指针作为对外接口。处理该socket线程、在线用户表以及向该socket发送信息的线程均通过`connection->fd`访问socket避免产生竞争，同时避免描述符被提前关闭或复用。



#### 1.4 共享数据与发送同步

**用户表锁**

`users_mutex` 保护在线表的插入、遍历和删除。使用 `lock_guard` 管理锁的作用域，退出作用域时自动解锁。业务处理和网络等待放在锁外，缩短其他线程等待访问名单的时间。

**连接发送锁**

每个 `Connection` 保存一个通信 fd 和独立的 `send_mutex`。`Connection::send` 取得锁后调用整个 `send_message`，将头部和负载作为一个整体保护，防止同一连接的多个发送者交错写入协议帧。不同连接使用不同的锁。

### 2. 消息收发过程

#### 2.1 帧结构

使用手册中方案A：固定8字节头部 + UTF-8 JSON负载。用长度字段确定每条消息的结束位置。

| Index | 字段 | 长度 | 内容 |
| --- | --- | --- | --- |
| 0～1 | 魔数 | 2 字节 | ASCII `CH` |
| 2 | 版本 | 1 字节 | 固定为 `1` |
| 3 | 消息类型 | 1 字节 | 无符号编号，见下表 |
| 4～7 | 负载长度 | 4 字节 | 无符号 32 位整数，大端序 |
| 8～ | 负载 | 长度字段指定的字节数 | UTF-8 JSON |



发送端先序列化JSON、检查长度，再组装头部，使用 `send_all` 完整发送头部和负载。接收端使用 `recv_exact` 先读8字节校验头部和长度，再分配空间读取负载并解析JSON。

#### 2.2 发送流程

`send_message`检查负载为 JSON 对象，通过`dump()`序列化，检查编码后的长度不超过 4 MiB，再组装头部。长度使用`htonl`转为网络字节序，通过`memcpy`写入头部。随后分别调用`send_all`发送完整头部和负载。若JSON编码异常将被捕获并返回失败。

#### 2.3 接收流程

`recv_message` 先用 `recv_exact` 指定读8字节长度的头部，检查魔数、版本和类型，再用 `ntohl` 还原正文长度并检测是否合法；检查通过后才分配字符串空间读取负载，解析 JSON 并确认结果是对象。所有校验通过后才更新输出消息对象。

非法头部、超限负载或 JSON 解析失败会输出本地诊断并返回失败。服务端结束该连接的处理循环并清理资源，不尝试从错误数据中重新寻找帧起点。

#### 2.4 连接结束与资源清理

`handle_client` 通过 `make_shared` 创建连接对象，登录成功后在线表持有同一对象。复制共享指针不会复制 socket 或锁。连接对象禁止拷贝，最后一个共享持有者释放它时，析构函数调用 `close`关闭资源

接收结束或收发返回失败后，处理线程在锁内查找自己的用户名，并确认对应值仍是当前连接，再删除条目。随后调用 `shutdown` 停止收发。处理函数不手动关闭连接描述符，避免其他共享持有者使用期间描述符被释放并复用。

客户端的 `/quit` 在本地结束输入循环，不发送协议退出消息。收尾按 `shutdown → receiver.join → close` 执行：停止收发，等待接收线程退出，再释放描述符。终端输入结束或发送失败也进入这一收尾流程。

### 3. 请求类型与响应格式

负载均为JSON对象。

| 编号 | 类型 | 客户端请求负载 | 服务端行为 |
| --- | --- | --- | --- |
| 1 | `Login` | `{"username":"alice"}` | 检查用户名和重名情况，为当前连接绑定身份 |
| 2 | `List` | `{}` | 返回当前在线用户名列表 |
| 3 | `Broadcast` | `{"text":"大家好"}` | 投递给其他所有已登录用户 |
| 4 | `Private` | `{"to":"bob","text":"你好"}` | 向目标用户投递讯息 |
| 5 | `Response` | 不允许作为客户端请求 | 服务端返回成功响应 |
| 6 | `Error` | 不允许作为客户端请求 | 服务端返回错误响应 |

服务端响应格式：

| 类型 | 场景 | JSON 示例 |
| --- | --- | --- |
| `Response` | 登录成功 | `{"request":"login","username":"alice"}` |
| `Response` | 在线列表 | `{"request":"list","users":["alice","bob"]}` |
| `Response` | 群发处理成功 | `{"request":"broadcast"}` |
| `Response` | 私聊处理成功 | `{"request":"private"}` |
| `Broadcast` | 发送群聊 | `{"from":"alice","text":"大家好"}` |
| `Private` | 发送私聊 | `{"from":"alice","text":"你好"}` |
| `Error` | 操作失败 | `{"request":"private","code":"USER_OFFLINE","message":"目标用户不在线"}` |

### 4. 各请求的实现设计

#### 4.1 登录请求（Login）

客户端命令 `/login alice` 生成：

```json
{"username":"alice"}
```

请求类型为 `Login`。服务端按以下顺序检查：

1. 当前连接是否已经登录。
2. `username` 字段是否存在且为字符串。
3. 名称是否为 1～32 个 ASCII 字母、数字或下划线。
4. 名称是否已被在线连接占用。

用户名区分大小写。在线表通过锁内的 `emplace` 完成唯一性判断和插入，避免先检查后插入产生竞态。插入成功后保存当前连接的身份，返回 `Response`：

```json
{"request":"login","username":"alice"}
```

失败时返回错误响应，保留连接，允许用户继续提交请求。

#### 4.2 在线列表请求（List）
在线表使用 `unordered_map<string, shared_ptr<Connection>>`，用户名为键、连接对象的共享智能指针为值。每个 `handle_client` 调用有一个局部 `username`：空字符串表示未登录，登录成功后保存当前身份。

客户端命令 `/list` 发送类型为 `List`、负载为 `{}` 的请求。服务端先检查当前连接已登录，然后在用户表锁内将用户名复制到本地 `vector`。释放锁后排序并生成 `Response`：

```json
{"request":"list","users":["alice","bob"]}
```

该列表是复制时刻的快照。排序使返回顺序稳定；锁内只做共享数据访问，不在持有用户表锁时进行网络发送。

#### 4.3 共用错误响应（Error）

错误响应类型为 `Error`。负载包含三个字符串字段：`request` 标明请求，`code` 是供程序识别的稳定错误码，`message` 是给用户看的说明。如：

```json
{"request":"login","code":"USERNAME_TAKEN","message":"username已占用"}
```

错误码常量集中放在 `common/error_codes.h`，业务代码使用常量名称，JSON 中发送其字符串值。

| 错误码 | 触发条件 | 请求名称 |
| --- | --- | --- |
| `ALREADY_LOGGED_IN` | 已登录的连接再次提交登录请求 | `login` |
| `INVALID_ARGUMENT` | 登录字段缺失、字段不是字符串或用户名格式非法 | `login` |
| `USERNAME_TAKEN` | 用户名已存在于在线表 | `login` |
| `NOT_LOGGED_IN` | 未登录就试图进行操作 | `list` |
| `UNEXPECTED_TYPE` | 协议类型有效，但没有匹配的业务处理分支 | `unknown` |

这些业务错误由处理函数构造为 `Message`，通过连接的统一发送入口返回，之后继续接收请求。协议解码失败和系统收发失败则通过函数返回值结束连接处理。系统 `errno` 用于本地诊断，不直接作为业务错误码传输。

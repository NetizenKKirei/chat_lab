## 阶段1：命令行聊天


### 帧结构

使用手册中方案A：固定8字节头部 + UTF-8 JSON负载。用长度字段确定每条消息的结束位置。

| Index | 字段 | 长度 | 内容 |
| --- | --- | --- | --- |
| 0～1 | 魔数 | 2 字节 | ASCII `CH` |
| 2 | 版本 | 1 字节 | 固定为 `1` |
| 3 | 消息类型 | 1 字节 | 无符号编号，见下表 |
| 4～7 | 负载长度 | 4 字节 | 无符号 32 位整数，大端序 |
| 8～ | 负载 | 长度字段指定的字节数 | UTF-8 JSON |



发送端先序列化JSON、检查长度，再组装头部，使用 `send_all` 完整发送头部和负载。接收端使用 `recv_exact` 先读8字节校验头部和长度，再分配空间读取负载并解析JSON。


### 消息类型与字段

负载均为JSON对象。

| 编号 | 类型 | 客户端请求负载 | 服务端行为 |
| --- | --- | --- | --- |
| 1 | `Login` | `{"username":"alice"}` | 检查用户名和重名情况，为当前连接绑定身份 |
| 2 | `List` | `{}` | 返回当前在线用户名列表 |
| 3 | `Broadcast` | `{"text":"大家好"}` | 投递给其他所有已登录用户 |
| 4 | `Private` | `{"to":"bob","text":"你好"}` | 向目标用户投递讯息 |
| 5 | `Response` | 不允许作为客户端请求 | 服务端返回成功响应 |
| 6 | `Error` | 不允许作为客户端请求 | 服务端返回错误响应 |

服务端响应和投递格式：

| 类型 | 场景 | JSON 示例 |
| --- | --- | --- |
| `Response` | 登录成功 | `{"request":"login","username":"alice"}` |
| `Response` | 在线列表 | `{"request":"list","users":["alice","bob"]}` |
| `Response` | 群发处理成功 | `{"request":"broadcast"}` |
| `Response` | 私聊处理成功 | `{"request":"private"}` |
| `Broadcast` | 发送群聊 | `{"from":"alice","text":"大家好"}` |
| `Private` | 发送私聊 | `{"from":"alice","text":"你好"}` |
| `Error` | 操作失败 | `{"request":"private","code":"USER_OFFLINE","message":"目标用户不在线"}` |

### 错误码定义

以下为第一版协议约定，不代表所有错误处理均已实现。错误响应的帧类型为 `MessageType::Error`（编号 `6`），负载格式为：

```json
{
  "request": "login",
  "code": "USERNAME_TAKEN",
  "message": "用户名已被占用"
}
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `request` | 字符串 | 对应请求名称：`login`、`list`、`broadcast`、`private`；无法识别或不属于客户端请求时为 `unknown` |
| `code` | 字符串 | 稳定的错误标识，客户端据此判断如何处理；不是头部的消息类型编号 |
| `message` | 字符串 | 给用户看的错误说明，措辞可以调整，客户端不应通过匹配这段文字判断错误类型 |

#### 协议与格式错误

| 错误码 | 定义与触发条件 | 连接处理 |
| --- | --- | --- |
| `INVALID_FRAME` | 魔数不是 `CH`，或负载长度为 `0` 等非法帧头 | 尝试发送错误响应后关闭连接 |
| `UNSUPPORTED_VERSION` | 版本号不是当前支持的 `1` | 尝试发送错误响应后关闭连接 |
| `UNKNOWN_TYPE` | 消息类型编号不在已定义的 `1`～`6` 中 | 尝试发送错误响应后关闭连接 |
| `PAYLOAD_TOO_LARGE` | 头部声明的 JSON 负载长度超过 4 MiB（4,194,304 字节，不含头部） | 在分配负载空间前拒绝，不继续读取负载，尝试发送错误响应后关闭连接 |
| `INVALID_JSON` | 收齐负载后发现 JSON 语法或 UTF-8 编码不合法，或解析结果不是 JSON 对象 | 尝试发送错误响应后关闭连接 |

协议错误时不能假设后续数据仍位于下一帧的起点，因此第一版统一关闭连接，不尝试重新定位帧边界。错误响应仅尽力发送，须限制发送等待时间；对端已经断开或不能写入时直接清理连接，不能保证对端收到错误。

#### 业务错误

以下错误在收到完整合法帧后检查。返回错误响应后保留请求方连接，允许后续请求。

| 错误码 | 定义与触发条件 | 客户端处理建议 |
| --- | --- | --- |
| `INVALID_ARGUMENT` | 必需字段缺失、字段类型错误、用户名格式非法或正文为空 | 提示用户修改输入后重试 |
| `UNEXPECTED_TYPE` | 类型编号有效，但该方向不允许使用，例如客户端发送 `Response` 或 `Error` | 修正请求类型；开发期间也可用于标识暂未实现的请求，交付前须实现约定的四种客户端请求 |
| `NOT_LOGGED_IN` | 未登录就请求在线列表、群聊或私聊 | 先登录，再执行操作 |
| `ALREADY_LOGGED_IN` | 当前连接已经登录，又发送 `Login` | 继续使用当前身份；切换身份需重新连接 |
| `USERNAME_TAKEN` | 请求的用户名已被其他在线连接占用 | 更换用户名后重试 |
| `USER_OFFLINE` | 私聊目标不在在线用户表中 | 提示目标不在线，可重新查询在线列表 |
| `MESSAGE_TOO_LARGE` | JSON 解析后 `text` 的 UTF-8 字节数超过 1 MiB（1,048,576 字节） | 缩短正文后重试 |
| `DELIVERY_FAILED` | 投递时向目标连接发送失败，例如目标在查询后断开 | 提示投递失败；服务端清理失败的目标连接，发送者仍连接时向其返回错误 |

用户名约定为 1～32 个 ASCII 字母、数字或下划线，区分大小写。`username`、`to`、`text` 均要求为 JSON 字符串；空白正文允许，空字符串正文不允许。

`PAYLOAD_TOO_LARGE` 限制整个编码后的 JSON，`MESSAGE_TOO_LARGE` 限制解析后的正文，两者不可混用。恰好等于各自上限时不因长度而拒绝；只有超过上限才报错。若协议长度已经超限，先报告协议错误，不再解析正文。

登录检查顺序为：是否已登录 → 字段存在且为字符串 → 用户名格式 → 名称是否被占用。其他已实现业务先检查登录状态，再检查业务字段。每个失败请求返回一个错误响应，不在同一请求后再发送成功响应。

群发发生部分投递失败时，已送达其他连接的消息不能回滚，发送者可能收到 `DELIVERY_FAILED`；客户端不应自动重发，以免其他用户收到重复消息。发送成功只表示字节交给系统，不代表接收者已经阅读。

#### 与系统错误的区别

`errno`（例如 `EINTR`、`EPIPE`）用于本地系统调用诊断，不直接作为上述业务错误码发送。`EINTR` 按收发函数约定重试；无法恢复的收发错误、对端结束发送或半帧断开应结束当前连接并清理在线状态，不交付不完整的消息给业务层。

当前 `bool recv_message(...)` 只能表示成功或失败，尚不能向调用者区分协议错误、正常断开和系统错误。实现上述错误反馈前，需要扩展接收结果，携带错误类别及相应错误码；不能仅打印到服务端终端就视为已经通知客户端。

# 单客户端压力测试设计

## 1. 目标与职责

测试链路：客户端发送 Test → 服务端接收并原样回显 → 客户端接收回显。

- 服务端与客户端分别持有自己的测试状态、接收统计。
- 两端采用相同的统计口径，在自己的终端输出实时信息与最终结果。
- 服务端不向客户端发送统计报告。
- 客户端主线程发送，接收线程是 socket 的唯一读取者。
- 服务端继续在 session 的接收循环中顺序统计和回显。
- 普通数据异常记录后继续；连接、帧解析或控制流程无法继续时才结束测试。

回环测试观察的是整个应用链路的处理能力；服务端同步回显也可能受客户端接收速度影响，不能把最终吞吐直接当作纯服务端接收能力。

## 2. 消息与完成条件

TestControl = 8，Test = 7，保持现有协议帧格式。

开始请求：

```json
{"phase":"start","run_id":0,"message_count":100000,"data_bytes":1024}
```

服务端验证参数、初始化本 session 的测试状态，返回：

```json
{"phase":"start_ack","run_id":0}
```

客户端收到确认后开始发送 Test，sequence 从 0 递增，data 为固定字符 x：

```json
{"sequence":0,"data":"xxxxxxxx"}
```

发送计划完成后发送：

```json
{"phase":"end","run_id":0}
```

服务端输出自己的最终统计，返回：

```json
{"phase":"end_ack","run_id":0}
```

当前服务端逐条处理并同步发送回显，因此 end_ack 排在此前所有回显之后。客户端收到 end_ack 即结束本轮统计，不因接收数不足继续等待不存在的回显。以后若改成异步回显，必须仍保证 end_ack 在全部回显之后发送。

服务端在连接中断时输出已有统计。客户端目前失败后提示错误并退出本轮，
然后尝试下一轮；控制等待尚未设置超时，失败路径也尚未统一输出完整统计。

## 3. 统一接收统计口径

| 字段 | 含义 |
|---|---|
| expected_messages | 开始时约定的 Test 总数 |
| received_messages | 成功解码、识别为 Test 的消息数，包含业务字段错误的消息 |
| received_bytes | 可读取的 data 字符串字节数，不含 JSON 和协议头 |
| next_expected_sequence | 下一条期望序号，初始为 0 |
| data_errors | Test字段、顺序或内容错误，每条最多计一次；完整帧JSON解析失败也计入此项 |

每条 Test 先增加 received_messages。可读取的 data 字节累加到 received_bytes。
序号能合法解析时：

```cpp
if (sequence != stats.next_expected_sequence) {
    data_error = true;
}
stats.next_expected_sequence = sequence + 1;
```

序号不可解析时记录 data_errors，不更新期望序号。当前测试由客户端生成正常范围内的递增序号。

例如 0、1、3、4、5 只记录一次序号错误。重复和乱序不单独分类，不使用逐序号接收标记表。

结束时比较 expected_messages 和 received_messages：

- 少收：缺少数 = expected_messages - received_messages；
- 多收：多收数 = received_messages - expected_messages。

先比较再相减，避免无符号整数下溢。该指标是应用层数量差额，不是 TCP 网络丢包数；重复与缺失可能互相抵消。实时差额只表示尚未收到的数量，不提前判定为丢失。

## 4. 状态与函数结构

服务端：

- ServerTestState：active、run_id、expected_data_bytes，以及本轮统计。
- 状态和处理实现位于 server/test_session.h、server/test_session.cpp；session.cpp负责分发和连接清理。
- 在 handle_client 中创建局部实例，一条连接一个实例。
- handle_test_control(request, state)：start 初始化，end 输出并结束。
- handle_test(request, state)：统计异常与字节数，随后原样回显。
- 统计更新与打印提取为小函数，实时和最终输出共用格式。
- session 单线程访问自己的状态，不额外添加锁。

客户端：

- 接收统计口径与服务端一致，保存独立实例。
- 控制阶段用于等待 start_ack、end_ack 或致命失败，不将数据异常作为终止状态。
- mutex 和 condition_variable 用于主线程与接收线程共享状态及通知。
- 接收线程分发控制消息和 Test，主线程不调用 recv_message。
- 退出时先 shutdown 唤醒阻塞接收，再 join，最后由 UniqueFd 关闭描述符。

## 5. 异常处理

继续统计：序号不符、字段不合法、data 长度或内容错误。
完整帧已消费但 JSON 无法解析时增加 data_errors，继续读取下一帧，不增加接收消息数。
服务端对可识别的 Test 即使业务校验失败也原样回显，让客户端独立观察。

结束测试：连接关闭、帧边界无法信任、控制请求无法建立有效测试流程，或发送返回Close。Test发送返回Rejected时只增加拒绝数并继续。控制等待超时为后续待实现功能。
数据异常不得通过一个统一的 Error 响应意外触发客户端终止。

控制字段须校验类型、数值范围和当前阶段；活动测试中不允许 start 静默重置统计，end 必须匹配本轮 run_id。

## 6. 速率、时间与输出

启动方式：`pressure_test [目标MiB/s] [主机名或IP] [端口]`，默认10 MiB/s、127.0.0.1、9000。
一次启动依次执行两轮：run_id=0、每条1 MiB；run_id=1、每条1 KiB。
两轮均按10秒计算计划数量，各自新建连接和状态，间隔1秒，不追加汇总对比。
计划数量取目标字节速率乘持续时间再除以 data 大小，明确取整，确保数量与大小有效。
相同目标负载速率分别运行大消息低频、小消息高频两种组合。
目标速率不保证实际达到；发送阻塞可能延长实际测试时间。
限速采用固定起点加浮点秒偏移的sleep_until，落后于计划时直接发送。
首条立即发送，最后一条安排在第N-1个间隔，因此低消息频率下可能提前一个间隔完成，
短轮次平均吞吐也可能略高于目标。

两端每秒输出接收数、消息速率、负载 MiB/s、序号错误和数据错误，禁止逐条打印。
统计周期用本进程 steady_clock；平均速率采用本端开始统计至结束的实际时长，两端口径一致但数值不要求相等。
实时速率用本周期计数差除以实际周期时长。
若在接收循环内按时间检查输出，无消息时不会刷新；若需要停流期间仍每秒显示，后续加入独立定时输出并同步读取统计。

最终输出约定数、接收数、缺少或多收数、负载字节、异常计数、耗时与平均速率，以及正常结束或中断状态。
客户端额外统计实际发送数量、发送拒绝数与速率；发送拒绝不计入接收数据错误。实时进度输出当前周期内成功调用 `send_message` 的平均和最大应用发送耗时，不在最终摘要重复输出。最终摘要的 `drain_time` 从发送循环结束计算到收到 `end_ack`，包含结束控制帧的发送与往返时间。后续加入 RTT，不扩展服务端控制响应内容。

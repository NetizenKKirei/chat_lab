## 阶段1：命令行聊天

### 1. 整体结构

系统由客户端、服务端和共用通信模块组成。客户端将命令编码为请求；服务端接收完整消息，按请求类型调用业务处理函数，再通过连接对象返回响应。协议层负责消息格式，网络层负责字节收发。

以`message`作为消息基本单位，包含请求类型以及JSON格式正文。

```text
客户端命令 → Message → 协议编码 → TCP
                                  ↓
客户端显示 ← 协议响应 ← 请求处理 ← 协议解码
```

#### 1.1 工程与模块组织

| 文件 | 职责 |
| --- | --- |
| `common/net.h`、`common/net.cpp` | 循环收发指定数量的字节，处理部分读写及信号中断 |
| `common/protocol.h`、`common/protocol.cpp` | 定义消息对象，编码和解析协议帧 |
| `common/error_codes.h` | 集中定义错误码字符串 |
| `server/main.cpp` | 创建监听 socket、接受连接、启动工作线程 |
| `server/session.h`、`server/session.cpp` | 业务处理：登录、在线列表、群聊、私聊、请求分发及连接结束后的用户清理 |
| `server/connection.h` | 管理通信fd生命周期和帧发送锁 |
| `client/main.cpp` | 解析终端命令、发送请求、独立接收并显示消息 |

#### 1.2 网络与并发模型

服务端采用一连接一线程。主线程循环调用`accept`，将返回的通信描述符交给分离的工作线程执行`handle_client`，随后继续接受新连接。每个工作线程顺序接收、处理和响应本连接的请求。监听socket由主线程管理，通信socket由对应的**连接对象**管理。

客户端主线程负责键盘输入和发送，另一个接收线程持续调用 `recv_message` 并显示 JSON。只有接收线程读取 socket，避免多个读取者分走同一帧的数据。接收过程不依赖用户是否正在输入。

#### 1.3 连接对象与在线用户表

管理通信socket的结构体`Connection`，包含该socket的文件描述符以及对应的线程锁，使用共享智能指针作为对外接口。处理该socket的线程、在线用户表以及发送线程共享同一个对象，避免描述符被提前关闭或复用。共享智能指针管理对象寿命，发送同步由 `Connection::send` 内的锁保证；读取仍由本连接的处理线程负责。



在线表类型为 `unordered_map<string, shared_ptr<Connection>>`，保存“用户名 → 连接对象智能指针”的对应关系。`Connection` 自身保存 `fd` 和 `send_mutex`，不保存用户名；身份由 `handle_client` 的局部 `username` 记录。

这里的 `fd` 是服务端 `accept` 返回的通信描述符，不是客户端进程中的描述符，也不是服务端监听描述符。客户端刚连接时就创建连接对象，登录成功后才加入在线表。表中的智能指针与处理线程持有同一个对象，不复制 socket。

#### 1.4 共享数据与发送同步

**用户表锁**

`users_mutex` 保护在线表的插入、遍历和删除。使用 `lock_guard` 管理锁的作用域，退出作用域时自动解锁。业务处理和网络等待放在锁外，缩短其他线程等待访问名单的时间。

**连接发送锁**

每个 `Connection` 保存一个通信 fd 和独立的 `send_mutex`。`Connection::send` 取得锁后调用整个 `send_message`，将头部和负载作为一个整体保护，防止同一连接的多个发送者交错写入协议帧。不同连接使用不同的锁。

### 2. 消息收发过程

#### 2.1 帧结构

使用手册中方案A：固定8字节头部 + UTF-8 JSON负载。用长度字段确定每条消息的结束位置。

字段偏移、编码和长度上限见 [通信协议](protocol.md)。

发送端先序列化JSON、检查长度，再组装头部，使用 `send_all` 完整发送头部和负载。接收端使用 `recv_exact` 先读8字节校验头部和长度，再分配空间读取负载并解析JSON。

#### 2.2 发送流程

`send_message`检查负载为 JSON 对象，通过`dump()`序列化，检查编码后的长度不超过 4 MiB，再组装头部。长度使用`htonl`转为网络字节序，通过`memcpy`写入头部。随后分别调用`send_all`发送完整头部和负载。发送前检查失败或 JSON 编码异常返回 `Rejected`，此时尚未写入任何帧字节；底层发送失败返回 `Close`，全部发送成功返回 `Success`。

#### 2.3 接收流程

`recv_message` 先用 `recv_exact` 指定读8字节长度的头部，检查魔数、版本和类型，再用 `ntohl` 还原负载长度并检测是否合法；检查通过后才分配字符串空间读取负载，解析 JSON 并确认结果是对象。所有校验通过后才更新输出消息对象。

非法头部、非法负载长度或底层接收失败返回 `Close`，不尝试从错误数据中重新寻找帧起点。完整读取负载后，JSON 解析失败或结果不是对象返回 `Rejected`；因为该帧已被完整消费，可以继续读取下一帧。

协议接口使用 `MessageStatus` 表示本地处理结果：

| 状态 | 含义 |
| --- | --- |
| `Success` | 一帧发送或接收成功 |
| `Rejected` | 本条消息不合法，但消息边界仍然明确，连接可以继续使用 |
| `Close` | 连接已结束、收发失败或无法安全继续解析，需要调用者结束处理并清理 |

这些枚举值只作为 C++ 函数返回值，不写入消息头或 JSON，也不替代线上 `Error` 消息。`send_message` 和 `recv_message` 本身不调用 `close`。

服务端接收返回 `Rejected` 时，发送 `INVALID_JSON` 错误并继续；客户端接收返回 `Rejected` 时，提示并忽略。客户端发送返回 `Rejected` 时允许重新输入。服务端发送自己构造的业务响应或错误响应时，任何非 `Success` 结果都会结束当前连接处理；群聊、私聊的目标投递则分别处理 `Rejected` 与 `Close`。

#### 2.4 连接结束与资源清理

`handle_client` 通过 `make_shared` 创建连接对象，登录成功后在线表持有同一对象。复制共享指针不会复制 socket 或锁。连接对象禁止拷贝，最后一个共享持有者释放它时，析构函数调用 `close` 释放服务端本地 socket 资源。

接收返回 `Close` 或响应发送未成功时，处理线程在锁内查找自己的用户名，并确认对应值仍是当前连接，再删除条目。随后调用 `shutdown` 停止收发。处理函数不手动关闭连接描述符，避免其他共享持有者使用期间描述符被释放并复用。

客户端的 `/quit` 在本地结束输入循环，不发送协议退出消息。收尾按 `shutdown → receiver.join → close` 执行：停止收发，等待接收线程退出，再释放描述符。终端输入结束或发送返回 `Close` 也进入这一收尾流程；发送返回 `Rejected` 则继续输入。

客户端接收线程遇到 `Close` 时提示并退出该线程；这不会自动中断主线程中的 `getline`。最终清理由主线程退出输入循环后执行。

两端的 socket 分别属于各自进程。一端关闭连接后，另一端通过收发结果获知连接状态，仍需要释放自己的 socket。服务端通信连接的清理不关闭主线程的监听 socket。

### 3. 请求分发

`handle_client` 接收一个完整的 `Message` 后，根据 `type` 调用登录、列表、群聊或私聊处理函数。处理函数返回响应对象，再通过当前连接对象的 `send` 统一发送响应。消息编号、JSON 字段和响应格式集中在 [通信协议](protocol.md) 中定义。

### 4. 各请求的实现设计

#### 4.1 登录请求（Login）

请求类型为 `Login`。服务端按以下顺序检查：

1. 当前连接是否已经登录。
2. `username` 字段是否存在且为字符串。
3. 名称是否为 1～32 个 ASCII 字母、数字或下划线。
4. 名称是否已被在线连接占用。

用户名区分大小写。在线表通过锁内的 `emplace` 完成唯一性判断和插入，避免先检查后插入产生竞态。插入成功后保存当前连接的身份，返回包含用户名的 `Response`。

失败时返回错误响应，保留连接，允许用户继续提交请求。

#### 4.2 在线列表请求（List）
在线表使用 `unordered_map<string, shared_ptr<Connection>>`，用户名为键、连接对象的共享智能指针为值。每个 `handle_client` 调用有一个局部 `username`：空字符串表示未登录，登录成功后保存当前身份。

客户端命令 `/list` 发送类型为 `List`、负载为 `{}` 的请求。服务端先检查当前连接已登录，然后在用户表锁内将用户名复制到本地 `vector`。释放锁后排序并生成包含名单的 `Response`。

该列表是复制时刻的快照。排序使返回顺序稳定；锁内只做共享数据访问，不在持有用户表锁时进行网络发送。

#### 4.3 群聊请求（Broadcast）

`handle_broadcast` 先检查登录身份、正文字段类型、非空及正文长度。在用户表锁内将其他用户的连接共享指针复制到本地列表，排除发送者；解锁后组装包含服务端登录身份的投递消息，并逐个调用目标连接的 `send`。

目标列表中的共享指针保证投递期间连接对象仍存在。投递返回 `Close` 时对目标执行 `shutdown`，由对应处理线程清理在线状态；返回 `Rejected` 时只记录本次投递失败，保留目标连接。群聊处理继续尝试其他目标，最终向发送者返回操作结果。没有其他在线目标也返回错误。群发不具有原子性，部分投递失败不会撤销已经发送的消息。

#### 4.4 私聊请求（Private）

`handle_private` 检查登录、目标名和正文后，在用户表锁内通过 `find` 查询目标并复制共享指针。使用 `find` 而非 `operator[]`，避免查询不存在的名字时插入空条目。释放用户表锁后向唯一目标投递，再向请求者返回结果。

目标在查询后仍可能断开，因此发送结果必须检查；返回 `Close` 时停止目标连接的收发并返回投递失败错误；返回 `Rejected` 时保留目标连接并返回投递失败错误。查询时目标不存在则返回 `USER_OFFLINE`。允许私聊自己，投递和操作响应依次通过同一连接的发送入口，不同时持有该锁。

#### 4.5 共用错误响应（Error）

错误码常量集中放在 `common/error_codes.h`，业务代码使用常量名称，JSON 中发送其字符串值。`make_error` 将请求名称、错误码和说明组装成 `Message`，由连接处理函数统一发送。具体错误码和字段含义见 [通信协议的错误响应](protocol.md#6-错误响应与断开规则)。

业务错误响应发送成功后继续接收请求；协议层根据错误发生阶段返回 `Rejected` 或 `Close`，由调用者决定继续处理还是清理连接。系统 `errno` 用于本地诊断，不直接作为业务错误码传输。
